Implemented lib/tokenizer/template.mlpl. Decoding needed an id-to-token direction, which a 151,643-key reverse scan cannot provide; the vocabulary turns out to be written one entry per line in id order, and a byte-level token can never contain a real line break, so line id plus one holds the entry. The reader verifies each line's own id rather than trusting the ordering, so a differently ordered document errors instead of returning wrong text. Verified on the real vocabulary: ids 14990 and 1879 decode to hello world, and the base and reasoning end-of-sequence ids resolve to 151643 and 151645. Also implemented the inverse byte alphabet with a round trip checked across all 256 byte values, control-token splitting so a marker becomes its id rather than being merged byte by byte, the chat template with the thinking flag deciding whether the assistant turn is left open or given an empty reasoning block, bare-text rendering for the base model, and the end-of-sequence rule per kind. The base tokenizer has no reasoning tags in either its vocabulary or its control tokens, and u:tok_think_ids reports that rather than inventing ids. Seven tests cover all of it. While measuring decode speed I found that string-list indexing scales the same way record lookup does, and crucially that reading index 5 costs the same as index 50,000, so the cost follows container size rather than distance to the element, which points at copying on access rather than a linear scan; added probes/list-index-scaling.mlpl and broadened upstream request R10 to cover both containers with that evidence. 64 tests pass, eleven sources tangle, just check passes.
