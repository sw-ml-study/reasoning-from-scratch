1. Building the book's reasoning system

Sebastian Raschka's Build a Reasoning Model (From Scratch) develops reasoning methods around a pretrained language model. This project implements that approach in MLPL, using Rust and CUDA for native model execution. The experiment tools—prompting, generation control, answer verification, self-consistency and analysis—are MLPL programs. No Python runs in this implementation.

Our working demonstration uses Qwen3-0.6B-Base, the book's starting model, on a 16 GiB RTX 5060 Ti. On the author's first ten MATH-500 problems, direct prompting solves 3/10, greedy chain-of-thought solves 4/10, and voting across three sampled reasoning responses solves 6/10. All fifty model calls finish, with zero backend errors, in 38 minutes 22 seconds.

The demonstration establishes an inference-time reasoning benefit on this fixed sample. Two questions become correct through valid intermediate calculations in the greedy reasoning condition. Voting improves the net result further, although some individual questions regress. The full 500-problem benchmark remains planned work.

“From scratch” describes the implementation of the reasoning system and its methods. As in the book, we start with pretrained base weights; we do not pretrain a language model. In this experiment the 596,049,920 parameters remain fixed. MLPL training objectives and toy updates are implemented; training this native language model is a separate, unfinished stage.

This document is executable research. Six named ob-mlpl blocks run the production sampling and verification libraries, recompute the measured results, and illustrate reward normalization and a checked gradient update. Their outputs are recorded below and checked before publication.

The book uses Python and tensor/symbolic libraries. We independently implement the experiment semantics in MLPL. 3. Step 1: establish correct model execution

The Qwen3 checkpoint contains 310 BF16 tensors, about 1.19 GB of weights. Its architecture has 28 transformer layers, hidden width 1024, 16 query heads, eight key/value heads and a vocabulary of 151,936 tokens. The MLPL reference implements RMS normalization, rotary position encoding, grouped-query attention, SwiGLU and the tied output projection.

Generation first encodes the complete prompt. A forward call prefills the cache and returns scores for the next token. MLPL selects a token, appends it, and sends only that new token to the next forward call. Reusing cached keys and values avoids recomputing every earlier position. Each independent answer begins with an empty cache. The experiment uses context length 4096, up to 2048 generated tokens and EOS token 151643.

We compare native outputs to an independent MLPL F64 forward calculation. For the five-token input “The capital of France is”, the comparison covers all 151,936 final logits. Layer-by-layer reference execution bounds working memory while preserving the forward calculation.

Real checkpoint CUDA F32 vs MLPL F64 0.00000711613 Below 0.005
Real checkpoint CUDA BF16 vs MLPL F64 0.367154 Below 0.5

BF16 satisfies its declared tolerance but is not bit-identical to the reference. These checks validate this input and the tested cache behavior; they do not establish identical long generations across frameworks. The numerical measurements and provider instructions give the reproducible details.

4. Step 2: turn next-token scores into reasoning responses

A direct prompt asks for an answer. The chain-of-thought condition appends the author's step-by-step instruction. Both greedy conditions choose the highest-scoring next token. The same base weights can therefore produce different responses because the additional instruction changes the context on which each subsequent token is conditioned.

Self-consistency adds diversity: generate three independent responses to the reasoning prompt, extract their final answers, and choose the most frequent answer. Temperature controls the sharpness of the next-token distribution; top-p filtering retains the most probable tokens until their cumulative probability reaches the threshold, including the crossing token. Sampling then draws from the renormalized retained distribution.

4.1. Execute the sampler in MLPL

This three-token example calls the same sampling primitives used by the model runner. Logits log([1,2,4]) at temperature 1 give probabilities [1,2,4]/7. At top-p 0.8, tokens 2 and 1 cross the threshold, leaving probabilities [0,1/3,2/3] in token-ID order. Supplied uniforms 0 and 0.9 therefore select IDs 1 and 2. These are authored mathematical goldens, independent of any model-generated answer. 

# Production sampling primitives on an analytically known vocabulary.
include "../lib/scaling/scaling.mlpl";
probabilities = u:scaling_temperature(log([1, 2, 4]), 1)?
nucleus = u:scaling_nucleus(probabilities, 0.8)?
first = u:scaling_pick(nucleus, 0)?
last = u:scaling_pick(nucleus, 0.9)?
print("probabilities:", probabilities)
print("nucleus:", nucleus)
print("selected ids:", first, last)
if reduce(:and, lt(abs(probabilities - [1, 2, 4] / 7), 1e-12)) * reduce(:and, lt(abs(nucleus - [0, 1, 2] / 3), 1e-12)) * eq(first, 1) * eq(last, 2) {
  ok("sampling matches analytic probabilities and selected ids")
} else {
  err("sampling differs from analytic result")
}

The real experiment uses temperature 0.9, top-p 0.9, and seeds 43, 44 and 45 for its three responses per question. MLPL supplies an explicit uniform stream for each response. The seed numbers match the companion experiment; MLPL's xorshift stream differs from PyTorch's random stream, so matching seeds do not imply matching sampled tokens. Exact boundary and tie behavior is specified in the sampling contract.

5. Step 3: select an answer, then verify it

For each response, MLPL extracts the last complete boxed answer. If there is no box, it uses the final recognized number, then the whole text as a fallback. This follows the companion evaluation script's contract. Output that reaches the token budget still receives a grade.

Voting counts raw extracted strings. Ties select the first answer to appear. Only after choosing the winner do we normalize and grade it against the reference. The known correct answer never influences candidate selection. Thus 0.5 and 1/2 are distinct votes even though they denote the same number when graded.

7.4. Making the implementation faster

A matched performance experiment measures the cost of the MLPL/native boundary and token selection using an authored prompt. Native Rust sampling preserves the MLPL f64 distribution, supplied uniforms and selected token sequence. The resident step returns one token ID while MLPL retains seeds, controls and stopping. It improves sampled generation from 8.98 to 21.33 tokens/s: 2.37× faster on the same prompt and hardware.

Matched workload MLPL selection Native selection
Sampled, mean for 128 tokens (four pairs) 14.247 s 6.000 s
Greedy, mean for 128 tokens (two pairs) 5.604 s 5.059 s

Every paired token sequence is identical. These are capped performance traces on one authored prompt and seed, separate from answer accuracy. They do not establish a speedup over the book's Python implementation.

A longer acceptance pair uses a synthetic 1024-token prefill and forces 2048 sampled output tokens within context4096. All 2048 token IDs match exactly: reference selection takes 275.17 s and native selection 154.16 s (1.78× for this single pair). EOS is disabled for this test. It checks the full token budget and longer cache, not reasoning accuracy. The acceptance record and reproduction recipe retain these controls.

A fixed-vocabulary profile measures 96.29 ms per sampled token in MLPL: 15.11 ms for temperature/softmax, 57.47 ms for nucleus filtering and 23.71 ms for categorical selection. Native selection through the extension takes 12.18 ms. Repeated full-vector checks and normalization, two sorts and array copies are concrete optimization targets. The native selector eliminates the inverse sort and keeps vocabulary arrays inside the provider when using the resident step.

Kernel/driver tracing identifies where more speed is available. Across 48 fixed decode windows, mean elapsed time is 57.21 ms, summed kernel spans 4.66 ms, driver launch APIs 26.76 ms, allocation/free APIs 1.35 ms, and device-to-host APIs 9.67 ms. These timings overlap and must not be added. Each decode launches 814–817 kernels. Reducing launch traffic and testing reused pinned transfer buffers are therefore concrete next experiments.

The GPU context trace shows no switch to another process during the measured kernel window. A standalone Rust/Candle probe also reproduces recurring stalls without MLPL or model weights. The precise library/driver cause is still unresolved; no additional speedup is claimed from these diagnostics. See the trace analysis and reproduction commands and performance evidence for scope and source/build identities.

9. Learning from reasoning: implemented foundations and planned training

Inference-time scaling spends more computation with fixed weights. Reinforcement learning instead changes the probabilities of generating particular responses. The verifier supplies a reward, group-relative advantages identify better responses, and an optimizer updates a trainable policy. Distillation trains a student on checked teacher responses using answer-only loss. These are the book's later stages.

9.1. Compute group-relative advantages

For rewards [1,1,0,0], subtract the group mean and divide by the unbiased sample standard deviation plus epsilon. A constant-reward group supplies zero relative preference. This executable example checks that arithmetic; the full policy objective also needs sequence probabilities and masking. 

# Educational reward normalization, not a trained policy.
rewards = [1, 1, 0, 0]
centered = rewards - mean(rewards)
deviation = sqrt(reduce_add(centered * centered) / (tally(rewards) - 1))
advantages = centered / (deviation + 0.000001)
constant = [1, 1, 1, 1]
constant_advantages = (constant - mean(constant)) / 0.000001
print("rewards:", rewards)
print("sample deviation:", deviation)
print("advantages:", advantages)
print("constant-group advantages:", constant_advantages)
if eq(reduce_add(advantages), 0) * equal(constant_advantages, [0, 0, 0, 0]) {
  ok(1)
} else {
  err("reward-normalization check failed")
}

9.2. Execute and check a real parameter update

A small MLPL autograd example fits prediction=w*x to y=2*x for x[1,2,3,4]=. Starting at w=0, six gradient steps use learning rate 0.05. The analytic loss is 7.5*(w-2)^2 and its derivative is 15*(w-2), so each step quarters the distance to 2. The expected final weight and loss are known independently of the implementation. 

# Actual six-step scalar regression; no language-model weight is changed.
w = param[1]
w = [0]
x = [1, 2, 3, 4]
y = 2 * x
print("step 0 weight:", w, "loss:", mean((w * x - y) * (w * x - y)))
step = 0
while lt(step, 6) {
  derivative = grad(mean((w * x - y) * (w * x - y)), w);
  w = w - 0.05 * derivative;
  step = step + 1;
  print("step:", step, "weight:", w, "loss:", mean((w * x - y) * (w * x - y)))
}
final_loss = mean((w * x - y) * (w * x - y))
if equal(w, [1.99951171875]) * eq(final_loss, 0.0000017881393432617188) {
  ok("scalar training matches the analytic recurrence")
} else {
  err("scalar training differs from its golden result")
}

Native training acceptance must establish correct gradients, an actual parameter change, and identical predictions after saving and reloading a checkpoint. Reasoning improvement then requires separate training and held-out data, a no-update control, fixed evaluation settings and reported before/after accuracy.

10.2. Live execution supervision

An independent watchdog checks the immutable journal every minute without taking the writer lock. MLPL validates checksums, request identities and state transitions, then evaluates operational health. A local HTML dashboard reloads every minute and displays counts, tokens, caps, errors and the current call's age.

After confirming a fault twice, two seconds apart, the monitor stops only the verified experiment controller or pinned interpreter holding its journal lock. The triggers include a backend error, corrupt evidence, a disappeared worker, a ten-minute call or a five-minute idle gap. These conservative wall thresholds can interrupt an unusually slow valid call; such a call remains an interruption, not an incorrect mathematical answer or an automatically retried request. Mathematical accuracy and token caps alone do not trigger stopping. This keeps operational supervision separate from the frozen method comparison.

The acceptance fixtures test health thresholds, planned stops, observer failures, process scoping and an isolated native journal owner's termination. The live experiment continues with unchanged generation/source pins. This monitoring publishes local progress; it does not schedule future chat notifications.
