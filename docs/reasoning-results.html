1. What this project recreates

This project follows Sebastian Raschka's Build a Reasoning Model (From Scratch), Manning: start with a pretrained base language model, measure its answers, add inference-time reasoning methods, then develop learning from verifiable rewards and distillation. We implement the experiment tools in MLPL and use a Rust/CUDA dynamic library for practical model execution. Python is not part of this workflow.

The current demonstration uses Qwen3-0.6B-Base, the book's starting model, on a 16 GiB RTX 5060 Ti. MLPL prepares the author's first ten MATH-500 records, renders the prompts, selects tokens, extracts answers, votes, grades and computes the report. The Rust provider keeps weights and the attention cache on the GPU. No service or HTTP backend is involved.

Measured result: 3/10 correct with direct prompting, 4/10 with greedy chain-of-thought, and 6/10 with three-sample self-consistency. All fifty calls finished, with no backend errors. This demonstrates a benefit from reasoning plus voting on this fixed ten-problem sample. It does not yet establish the full book's 500-case results or a trained reasoning policy.

“From scratch” here means implementing the reasoning methods and their supporting tools. The 596,049,920 model parameters were pretrained by the checkpoint producer. This project has not yet trained this language model. The inference comparison measures the effect of changing how we use the same fixed weights.

2.1. Why this model is large enough for the experiment

The author's chapter 4 companion results report the following on all 500 MATH-500 questions, with a CUDA DGX Spark system:

Published method, same 0.6B base Correct Time
Greedy baseline 15.2% 10.1 min
Chain-of-thought prompting 40.6% 84.5 min
CoT with three sampled candidates 42.2% 211.6 min
CoT with ten sampled candidates 52.0% 862.6 min

Those results establish that this model size can benefit from these inference-time methods. They do not guarantee improvement on every small slice or every prompt. Our first-ten demonstration is too small to match the full benchmark claim. A different GPU, arithmetic and generated-token count also prevent a direct runtime comparison. Python/PyTorch already executes native CUDA kernels; replacing Python alone does not imply a hundredfold acceleration.

4. Step 2: freeze the book-aligned comparison

The protocol and execution manifest were committed before generation. The dataset is the author's JSON artifact, in its original order; there is no outcome-dependent selection or removal. We use the companion script's ten-case demonstration size and three sampled candidates. This is not a fresh held-out claim.

Control Value
Model Qwen3-0.6B-Base, BF16 weights/activations, fixed throughout
Direct Author's base completion prompt, greedy
CoT Same prompt plus the author's step-by-step instruction, greedy
Self-consistency CoT, temperature 0.9, top-p 0.9, three independent responses
Seeds Samples 43, 44, 45; greedy seed 42 is recorded but unused
Token allowance 2048 new tokens for each call; context 4096
Method schedule Rotate the three method groups by case index; reset KV per call
Total 10 direct + 10 CoT + 30 sampled responses = 50 calls
Selection Exact extracted strings; tied plurality chooses first appearance
Scoring Grade the selected answer, including output that reaches the cap

“Direct” names the base-prompt condition. The model can still emit intermediate calculations in that condition. CoT adds an explicit request for steps; sampling then explores different continuations from the same fixed model. Voting helps when a correct answer recurs more consistently than competing answers, and can fail when all candidates are wrong or when equivalent answers split across different raw strings.

Extraction first looks for the final complete boxed answer, then the final recognized number, then the whole response. A cap can interrupt a useful solution, but it does not automatically make an answer wrong. Conversely, correct final arithmetic does not establish that every intermediate step is valid. We report both answer accuracy and failures of completion.

The author revision is 1c0b9b17f80d335a9e7f73ca4738486bfa49fa9f. We follow its chapter 3 evaluator and chapter 4 evaluation script. The seed numbers match, but MLPL's pinned xorshift stream is not PyTorch's random stream. Numeric/tuple/literal and linear-symbolic grading covers the tested contracts; a full replacement for general symbolic simplification is still needed.

The whole job took 38 minutes 22 seconds from model loading through final recording. Dataset preparation precedes that clock. A single greedy CoT call averaged 43.4 seconds; a three-candidate voted answer averaged about 184 seconds. The longest sampled response took 267.6 seconds. Four responses reached the token cap, and none of those four verified as correct. There were no backend errors, deadline stops or missing method groups.

Decode timings include prompt prefill, native forward and MLPL token selection. They exclude final text decoding, grading and file writes. The aggregate rates were 19.87 tokens/s for direct, 18.28 for greedy CoT and 8.24 for sampling. Different trace lengths contribute to those rates; separate profiling is needed to attribute the overhead.

Sampled peak device-wide memory was 2,365 MiB, including desktop use, and observed process host high-water memory was 1,763,776 KiB (about 1.68 GiB). The roughly two-second device sampling can miss brief peaks. This inference run does not approach the GPU's 16 GiB capacity. See the observed provenance and memory definitions.

The fifty attempt records, thirty method outcomes and MLPL-computed summary retain all primary scores. The rendered prompt hashes and generation-source pins still match after the run. An offline replay of all fifty saved requests and responses matches the original grades.

These are descriptive results on ten fixed problems. Wilson intervals describe the uncertainty of such a small count; this ordered subset is not a random sample that justifies a full MATH-500 population claim. Paired gains and losses show which problems actually change outcome. Thirty sampled responses produce ten voted answers, not thirty independent evaluation problems.

5.1. What the failures tell us

The selected qualitative review checks saved responses without changing the primary scores. It separates several mechanisms:

  • Useful intermediate work: two greedy CoT gains use valid rational-function evaluation and divisor-counting steps. Direct answers to those same problems are wrong. These are concrete reasoning gains, not grader fixes.
  • Repetition and truncation: the first two greedy CoT responses reach the 2048-token cap while repeating rather than advancing a solution. More output allowance alone is not a demonstrated remedy for those traces.
  • Answer-format loss: another response correctly reads plotted values, computes rates and identifies the answer in prose, but omits its final box. The author's fallback extracts a numeric rate rather than the requested label. Its primary score remains wrong; the mathematical work is reviewed separately.
  • Sampling regression: all three sampled answers are wrong on one problem that direct answering and greedy CoT both solve. Voting has no correct candidate to select there. More compute is not a per-problem guarantee.

The selected review notes record the attempt IDs and categories. This is not an exhaustive proof of every generated step, and it does not replace the fixed answer metric. Unsupported general symbolic equivalence remains a known coverage gap; it should be diagnosed independently rather than used as an explanation for every wrong answer.

A short authored development prompt asks about a tank containing 120 liters, losing 35, then gaining 18. The base model produces the valid sequence 120−35=85 and 85+18=103, with final answer 103. 7. What establishes effective reasoning, and what comes next

Correct intermediate steps establish a worked example. A repeatable increase in paired answer accuracy establishes a useful reasoning method. Training requires a further result: a saved changed checkpoint that improves on held-out problems against the same starting policy and a no-update control. These are separate milestones.

The immediate next step is to make the demonstrated approach practical at book scale. Profile native forward execution, vocabulary transfer and MLPL sampling separately. Then offload the dominant cost through the extension, checking fixed-logit/supplied-uniform behavior against the MLPL reference. Preserve this completed experiment as the baseline. Improved performance must be measured rather than inferred from the implementation language.

Before running all 500 questions, strengthen symbolic-grading coverage with independently authored equivalence fixtures and freeze a resumable protocol with all cases in its denominator. Match the author's experiment controls and retain failures, token counts and elapsed time. A larger evaluation is needed to determine whether the observed gain generalizes.

Follow that with native language-model loss, backward, update and checkpoint acceptance. First verify a small update against analytic or finite-difference gradients and test save/reload. Only then run the book's learning methods on a separate training dataset and evaluate unchanged held-out problems. The scalar example below illustrates real updates, but it does not establish that native Qwen3 training has been implemented.

The relevant library and extension ecosystem remains the implementation path: demo-ml-utils, demo-mlpl-libraries, demo-extensions and the CUDA demos. The local inference provider is tested and pinned, but its source currently lives outside this repository. Publishing it through the extension project is a remaining dependency handoff. The repository's read-only sibling policy requires explicit authorization for that delivery.

8. Training: one real toy update, and the work still required for an LLM

No model weights changed during the direct, CoT or voting experiment. The MLPL verifier can supply a reward signal, but reward computation and parameter optimization are separate operations.

8.1. From checked answers to relative rewards

Suppose four independently sampled answers receive rewards [1,1,0,0]. Subtracting the group mean identifies better and worse samples relative to that group. Scaling by the unbiased sample standard deviation plus epsilon gives a dimensionless advantage. A constant-reward group supplies no relative preference. This block illustrates that arithmetic only; it does not implement the complete GRPO objective or a policy update. 

# Educational reward normalization, not a trained policy.
rewards = [1, 1, 0, 0]
centered = rewards - mean(rewards)
deviation = sqrt(reduce_add(centered * centered) / (tally(rewards) - 1))
advantages = centered / (deviation + 0.000001)
constant = [1, 1, 1, 1]
constant_advantages = (constant - mean(constant)) / 0.000001
print("rewards:", rewards)
print("sample deviation:", deviation)
print("advantages:", advantages)
print("constant-group advantages:", constant_advantages)
if eq(reduce_add(advantages), 0) * equal(constant_advantages, [0, 0, 0, 0]) {
  ok(1)
} else {
  err("reward-normalization check failed")
}

Reward alone does not specify which token probabilities should change. An LLM training implementation also needs differentiable sequence log probabilities, an explicit masking convention, policy ratios, clipping and any reference-policy regularization, an optimizer, and checkpointing. Those steps must be tested before a reward improvement can be called an LLM training result.

8.2. A small, actual MLPL training experiment

To make the difference concrete, fit the scalar model prediction=w*x to y=2*x for x[1,2,3,4]=. This is deterministic supervised regression, not reasoning-model training. Initialize w=0, compute the gradient of the mean squared error, and make six gradient-descent updates at rate 0.05.

The loss is 7.5*(w-2)^2, so its derivative is 15*(w-2). Each update therefore quarters the distance from w to 2. This independent analytic recurrence gives exact acceptance values: after six steps w=1.99951171875 and loss 0.0000017881393432617188. The native test suite checks these values, rather than merely asserting that some number decreased. 

# Actual six-step scalar regression; no language-model weight is changed.
w = param[1]
w = [0]
x = [1, 2, 3, 4]
y = 2 * x
print("step 0 weight:", w, "loss:", mean((w * x - y) * (w * x - y)))
step = 0
while lt(step, 6) {
  derivative = grad(mean((w * x - y) * (w * x - y)), w);
  w = w - 0.05 * derivative;
  step = step + 1;
  print("step:", step, "weight:", w, "loss:", mean((w * x - y) * (w * x - y)))
}
final_loss = mean((w * x - y) * (w * x - y))
if equal(w, [1.99951171875]) * eq(final_loss, 0.0000017881393432617188) {
  ok("scalar training matches the analytic recurrence")
} else {
  err("scalar training differs from its golden result")
}

8.3. The next training evidence we would require

Start with a tiny trainable policy on a synthetic task with known rewards. Keep training and evaluation examples separate; measure a before/after change over fixed evaluation seeds; retain the old policy and a no-update control. Test constant rewards, masking, clipping boundaries and gradient signs. Only then test real-model gradient and memory feasibility.

The external native model can later generate candidate teacher responses, but responses must be checked before becoming a training corpus. Record which model produced them, preserve licensing/provenance, and prevent held-out evaluation questions from entering training. A native inference session is not a substitute for a differentiable student training path.
