* Building the book's reasoning system

Sebastian Raschka's [[https://www.manning.com/books/build-a-reasoning-model-from-scratch][Build a Reasoning Model (From Scratch)]] develops reasoning
methods around a pretrained language model. This project implements that
approach in *MLPL*, using *Rust and CUDA* for native model execution. The
experiment tools—prompting, generation control, answer verification,
self-consistency and analysis—are MLPL programs. No Python runs in this
implementation.

Our completed experiment uses *Qwen3-0.6B-Base*, the book's starting model,
on a 16 GiB RTX 5060 Ti. On all *500 MATH-500 problems*, direct prompting
solves *72/500 (14.4%)*, greedy chain-of-thought solves *213/500 (42.6%)*,
and three-sample voting solves *199/500 (39.8%)*. All 2500 model calls
complete with zero backend errors or interruptions. Chain-of-thought improves
answer accuracy by *28.2 percentage points*; voting does not improve on it.
Generation call time totals *18.86 hours*. The ten-case experiment below
provides a smaller worked example; the full-set results are the main evidence.

“From scratch” describes the implementation of the reasoning system and
its methods. As in the book, we start with pretrained base weights; we do
not pretrain a language model. In this experiment the 596,049,920 parameters
remain fixed. MLPL training objectives and toy updates are implemented;
training this native language model is a separate, unfinished stage.

This document is executable research. Seven named =ob-mlpl= blocks run the
production sampling and verification libraries, recompute the measured
results, and illustrate reward normalization and a checked gradient update.
Their outputs are recorded below and checked before publication.

* The book's approach and our implementation

The book progresses from generation and evaluation to inference-time
scaling, reinforcement learning with verifiable rewards, and distillation.
Our implementation follows those stages with the following division of work.

| Book stage | Method | Our implementation and evidence |
|------------+--------+---------------------------------|
| Chapter 2 and architecture appendix | Tokenize, run Qwen3, cache attention keys/values, generate tokens | Independent MLPL transformer/reference; native Rust tokenizer and Candle CUDA forward; numerical acceptance checks |
| Chapter 3 | Extract and grade answers; evaluate MATH-500 | MLPL text scanning, normalization, bounded equivalence and experiment accounting; measured full MATH-500 baseline |
| Chapter 4 | Chain-of-thought, temperature/top-p sampling, self-consistency | MLPL prompt and sampler contracts, raw-answer voting; measured direct/CoT/voting comparison |
| Chapter 5 | Score and refine candidate responses | MLPL scoring/refinement modules with fixture tests; real-checkpoint evaluation planned |
| Chapters 6–7 | Reward correct answers, compute group advantages, optimize a policy | MLPL reward/objective contracts and toy tests; native language-model backward/update path planned |
| Chapter 8 | Learn from checked teacher responses with answer-only loss | MLPL distillation contracts; native student training and held-out evaluation planned |

The book uses Python and tensor/symbolic libraries. We independently
implement the experiment semantics in MLPL. A native dynamic library uses
Rust Candle 0.11.0 and cudarc 0.19.10 to load the checkpoint and execute
transformer operations on CUDA. A tokenizer extension supplies practical
encoding and decoding. The independent MLPL reference and authored fixtures
check the native execution path.

The runtime boundary is deliberately small: MLPL sends token IDs to the
resident model and receives last-position logits. The provider owns model
weights and the attention cache; MLPL chooses each next token, stops at EOS
or a budget, extracts the answer, and computes the score. The full programs
and annotated library blocks are in the [[file:reasoning.org][implementation document]].

* Step 1: establish correct model execution

The Qwen3 checkpoint contains 310 BF16 tensors, about 1.19 GB of weights.
Its architecture has 28 transformer layers, hidden width 1024, 16 query
heads, eight key/value heads and a vocabulary of 151,936 tokens. The MLPL
reference implements RMS normalization, rotary position encoding,
grouped-query attention, SwiGLU and the tied output projection.

Generation first encodes the complete prompt. A forward call prefills the
cache and returns scores for the next token. MLPL selects a token, appends
it, and sends only that new token to the next forward call. Reusing cached
keys and values avoids recomputing every earlier position. Each independent
answer begins with an empty cache. The experiment uses context length 4096,
up to 2048 generated tokens and EOS token 151643.

We compare native outputs to an independent MLPL F64 forward calculation.
For the five-token input “The capital of France is”, the comparison covers
all 151,936 final logits. Layer-by-layer reference execution bounds working
memory while preserving the forward calculation.

| Numerical check | Maximum absolute difference | Acceptance |
|-----------------+-----------------------------+------------|
| Authored tiny CUDA F32 vs MLPL reference | 0.00000193084 | Below 0.00001 |
| Real checkpoint CUDA F32 vs MLPL F64 | 0.00000711613 | Below 0.005 |
| Real checkpoint CUDA BF16 vs MLPL F64 | 0.367154 | Below 0.5 |
| Real BF16 cached vs full-prompt calculation | 0.3125 | Below 0.5 |

All real-checkpoint paths choose token 12095, “Paris”. The F32 comparison
provides close numerical agreement on the tested input. BF16 satisfies its
declared tolerance but is not bit-identical to the reference. These checks
validate this input and the tested cache behavior; they do not establish
identical long generations across frameworks. The [[file:results/cuda-real-precision-v2.txt][numerical measurements]]
and [[file:cuda-prototype.md][provider instructions]] give the reproducible details.

* Step 2: turn next-token scores into reasoning responses

A direct prompt asks for an answer. The chain-of-thought condition appends
the author's step-by-step instruction. Both greedy conditions choose the
highest-scoring next token. The same base weights can therefore produce
different responses because the additional instruction changes the context
on which each subsequent token is conditioned.

Self-consistency adds diversity: generate three independent responses to
the reasoning prompt, extract their final answers, and choose the most
frequent answer. Temperature controls the sharpness of the next-token
distribution; top-p filtering retains the most probable tokens until their
cumulative probability reaches the threshold, including the crossing token.
Sampling then draws from the renormalized retained distribution.

** Execute the sampler in MLPL

This three-token example calls the same sampling primitives used by the
model runner. Logits =log([1,2,4])= at temperature 1 give probabilities
=[1,2,4]/7=. At top-p 0.8, tokens 2 and 1 cross the threshold, leaving
probabilities =[0,1/3,2/3]= in token-ID order. Supplied uniforms 0 and 0.9
therefore select IDs 1 and 2. These are authored mathematical goldens,
independent of any model-generated answer.

#+name: sampling-method
#+begin_src mlpl
# Production sampling primitives on an analytically known vocabulary.
include "../lib/scaling/scaling.mlpl";
probabilities = u:scaling_temperature(log([1, 2, 4]), 1)?
nucleus = u:scaling_nucleus(probabilities, 0.8)?
first = u:scaling_pick(nucleus, 0)?
last = u:scaling_pick(nucleus, 0.9)?
print("probabilities:", probabilities)
print("nucleus:", nucleus)
print("selected ids:", first, last)
if reduce(:and, lt(abs(probabilities - [1, 2, 4] / 7), 1e-12)) * reduce(:and, lt(abs(nucleus - [0, 1, 2] / 3), 1e-12)) * eq(first, 1) * eq(last, 2) {
  ok("sampling matches analytic probabilities and selected ids")
} else {
  err("sampling differs from analytic result")
}
#+end_src

The real experiment uses temperature 0.9, top-p 0.9, and seeds 43, 44 and 45
for its three responses per question. MLPL supplies an explicit uniform
stream for each response. The seed numbers match the companion experiment;
MLPL's xorshift stream differs from PyTorch's random stream, so matching
seeds do not imply matching sampled tokens. Exact boundary and tie behavior
is specified in the [[file:sampling.md][sampling contract]].

* Step 3: select an answer, then verify it

For each response, MLPL extracts the last complete boxed answer. If there
is no box, it uses the final recognized number, then the whole text as a
fallback. This follows the companion evaluation script's contract. Output
that reaches the token budget still receives a grade.

Voting counts *raw extracted strings*. Ties select the first answer to
appear. Only after choosing the winner do we normalize and grade it against
the reference. The known correct answer never influences candidate
selection. Thus =0.5= and =1/2= are distinct votes even though they denote
the same number when graded.

** Making the implementation faster

A matched performance experiment measures the cost of the MLPL/native
boundary and token selection using an authored prompt. Native Rust sampling
preserves the MLPL f64 distribution, supplied uniforms and selected token
sequence. The resident step returns one token ID while MLPL retains seeds,
controls and stopping. It improves sampled generation from *8.98 to 21.33
tokens/s*: *2.37× faster* on the same prompt and hardware.

| Matched workload | MLPL selection | Native selection |
|------------------+----------------+------------------|
| Sampled, mean for 128 tokens (four pairs) | 14.247 s | 6.000 s |
| Greedy, mean for 128 tokens (two pairs) | 5.604 s | 5.059 s |

Every paired token sequence is identical. These are capped performance
traces on one authored prompt and seed, separate from answer accuracy.
They do not establish a speedup over the book's Python implementation.

A longer acceptance pair uses a synthetic 1024-token prefill and forces
2048 sampled output tokens within context4096. All 2048 token IDs match
exactly: reference selection takes 275.17 s and native selection 154.16 s
(1.78× for this single pair). EOS is disabled for this test. It checks the
full token budget and longer cache, not reasoning accuracy. The
[[file:results/cuda-long-acceptance-summary.json][acceptance record]] and [[file:cuda-tracing.md][reproduction recipe]] retain these controls.


A fixed-vocabulary profile measures 96.29 ms per sampled token in MLPL:
15.11 ms for temperature/softmax, 57.47 ms for nucleus filtering and 23.71 ms
for categorical selection. Native selection through the extension takes
12.18 ms. Repeated full-vector checks and normalization, two sorts and array
copies are concrete optimization targets. The native selector eliminates
the inverse sort and keeps vocabulary arrays inside the provider when using
the resident step.

Kernel/driver tracing identifies where more speed is available. Across 48
fixed decode windows, mean elapsed time is 57.21 ms, summed kernel spans
4.66 ms, driver launch APIs 26.76 ms, allocation/free APIs 1.35 ms, and
device-to-host APIs 9.67 ms. *These timings overlap and must not be added.*
Each decode launches 814–817 kernels. Reducing launch traffic and testing
reused pinned transfer buffers are therefore concrete next experiments.

The GPU context trace shows no switch to another process during the measured
kernel window. A standalone Rust/Candle probe also reproduces recurring
stalls without MLPL or model weights. The precise library/driver cause is
still unresolved; no additional speedup is claimed from these diagnostics.
See the [[file:cuda-tracing.md][trace analysis and reproduction commands]] and
[[file:cuda-performance.md][performance evidence]] for scope and source/build identities.

* Learning from reasoning: implemented foundations and planned training

Inference-time scaling spends more computation with fixed weights.
Reinforcement learning instead changes the probabilities of generating
particular responses. The verifier supplies a reward, group-relative
advantages identify better responses, and an optimizer updates a trainable
policy. Distillation trains a student on checked teacher responses using
answer-only loss. These are the book's later stages.

** Compute group-relative advantages

For rewards =[1,1,0,0]=, subtract the group mean and divide by the unbiased
sample standard deviation plus epsilon. A constant-reward group supplies
zero relative preference. This executable example checks that arithmetic;
the full policy objective also needs sequence probabilities and masking.

#+name: reward-advantages
#+begin_src mlpl
# Educational reward normalization, not a trained policy.
rewards = [1, 1, 0, 0]
centered = rewards - mean(rewards)
deviation = sqrt(reduce_add(centered * centered) / (tally(rewards) - 1))
advantages = centered / (deviation + 0.000001)
constant = [1, 1, 1, 1]
constant_advantages = (constant - mean(constant)) / 0.000001
print("rewards:", rewards)
print("sample deviation:", deviation)
print("advantages:", advantages)
print("constant-group advantages:", constant_advantages)
if eq(reduce_add(advantages), 0) * equal(constant_advantages, [0, 0, 0, 0]) {
  ok(1)
} else {
  err("reward-normalization check failed")
}
#+end_src

** Execute and check a real parameter update

A small MLPL autograd example fits =prediction=w*x= to =y=2*x= for
=x=[1,2,3,4]=. Starting at =w=0=, six gradient steps use learning rate 0.05.
The analytic loss is =7.5*(w-2)^2= and its derivative is =15*(w-2)=, so each
step quarters the distance to 2. The expected final weight and loss are
known independently of the implementation.

#+name: toy-sgd
#+begin_src mlpl
# Actual six-step scalar regression; no language-model weight is changed.
w = param[1]
w = [0]
x = [1, 2, 3, 4]
y = 2 * x
print("step 0 weight:", w, "loss:", mean((w * x - y) * (w * x - y)))
step = 0
while lt(step, 6) {
  derivative = grad(mean((w * x - y) * (w * x - y)), w);
  w = w - 0.05 * derivative;
  step = step + 1;
  print("step:", step, "weight:", w, "loss:", mean((w * x - y) * (w * x - y)))
}
final_loss = mean((w * x - y) * (w * x - y))
if equal(w, [1.99951171875]) * eq(final_loss, 0.0000017881393432617188) {
  ok("scalar training matches the analytic recurrence")
} else {
  err("scalar training differs from its golden result")
}

* Full MATH-500 results: reasoning improves accuracy

All 2500 planned calls completed across all 500 questions, with zero backend
errors, zero interruptions and no pending requests. The fixed base weights
solve substantially more problems when prompted for intermediate steps.

| Method | Correct / 500 | Accuracy | Gain over direct |
|--------+---------------+----------+------------------|
| Direct, greedy | 72 | 14.4% | — |
| Chain-of-thought, greedy | 213 | 42.6% | +28.2 percentage points |
| Three sampled CoT responses, plurality vote | 199 | 39.8% | +25.4 percentage points |

CoT gains 158 correct answers and loses 17 relative to direct prompting, with
325 ties. Voting gains 52 and loses 66 relative to greedy CoT, with 382 ties.
The methods share the same 500 questions. These are final results under our
bounded MLPL grader, not a claim of general mathematical reliability: even
CoT misses 287 questions. Written explanations have not all been independently
checked for valid intermediate reasoning.

Voting uses three temperature-0.9/top-p-0.9 responses, while greedy CoT uses
one temperature-zero response. Thus this comparison changes both sampling
and aggregation. It does not isolate voting's effect on identical candidates.
We cannot attribute the voting deficit to a single cause from these totals.
Candidate correctness, answer-string fragmentation, ties and truncation are
useful next diagnostics; changing voting after seeing these answers would
require a separately labeled experiment.

* Execution and verification contracts

** Numeric grading and unfinished reasoning

The book's chapter 3 implementation uses SymPy integers and symbolic
simplification. Our MLPL evaluator uses bounded exact rationals and finite
floating arithmetic: nonfinite literals and subexpressions return a range
failure, integer powers use logarithmic work, and GCD has a finite work bound.
This handles out-of-range responses safely but does not provide arbitrary-
precision symbolic parity. See [[file:grading-overflow.md][the arithmetic contract and primary-source comparison]].

One observed greedy response illustrates why a long explanation is not proof
of reasoning quality. For the smallest positive multiple of 450 using only
zeros and ones, the model emits a one followed by repeated zeros until the
2048-token cap. Since 450 = 9 × 50, the answer must end in two zeros and contain
a positive multiple of nine ones. The smallest valid answer is 11111111100;
the generated digit sum of one proves its answer incorrect. A sampled response
lists multiples until its cap instead. Neither continuation solves the task.

All 500 cases are scored under the bounded grading revision. Repetition
stopping and verified refinement remain separate future comparisons; the
generation protocol and primary denominator remain fixed.

** Execution protocol

The [[file:book-full500-runner.md][MLPL runner]] prepares all 500 author-ordered cases: 500 direct answers,
500 greedy chain-of-thought answers and 1500 sampled answers for three-vote
selection. Its [[file:results/book-full500-v1-execution.json][execution manifest]], 1000 prompt hashes and 2500 request
identities were committed before benchmark generation. Execution started at
2026-10-01 03:09 UTC and finished on October 2 at approximately 09:52 UTC.
The completed numerical outcomes and runtime analysis appear above.

MLPL owns scheduling, seeds, stopping, grading and recovery decisions. A generic
Rust extension writes checksummed immutable records, syncing contents and the
directory before acknowledging publication. A started call without a response
becomes an interruption after restart; completed responses are never regenerated.
All 500 cases stay in each method's denominator, and voting requires all three
responses. An incomplete run is labeled incomplete. Fixture acceptance covers
replay, duplicates, corruption, an interrupted call and a backend error.

A ten-call authored CUDA smoke completes in 30.9 seconds, including 6.2 seconds
of loading, with no backend errors. Six responses reach its short 64-token cap;
this tests integration, not MATH-500 accuracy. The full experiment uses 2048 new
tokens and context 4096. A planning range of 15.3–24.6 hours combines existing
token counts with measured throughput; distribution shifts and long outputs
can increase runtime. The runner checks a 48-hour cumulative budget between
calls. It reports prefill and decode times including selection, memory samples,
truncations, interruptions, errors and paired method outcomes.

The [[file:cuda-transport.md][CUDA transport experiment]] rotates pageable transfer, pinned transfer and
captured-graph modes over two trials of an allocation-free 800-kernel sequence.
Graph replay reduces median forward time from about 1.16 ms to 0.55 ms in both
trials. Pinned buffers do not consistently eliminate transfer stalls. This is
a toy-kernel result, not a Qwen speedup or a Python comparison. Model graph
capture needs stable cache addresses and shapes, followed by numerical and
seeded-token parity and repeated end-to-end measurements.

** Live execution supervision

An independent [[file:book-full500-watchdog.md][watchdog]] checks the immutable journal every minute without
taking the writer lock. MLPL validates checksums, request identities and state
transitions, then evaluates operational health. A local HTML dashboard reloads
every minute and displays counts, tokens, caps, errors and the current call's age.

After confirming a fault twice, two seconds apart, the monitor stops only the
verified experiment controller or pinned interpreter holding its journal lock.
The triggers include a backend error, corrupt evidence, a disappeared worker,
a ten-minute call or a five-minute idle gap. These conservative wall thresholds
can interrupt an unusually slow valid call; such a call remains an interruption,
not an incorrect mathematical answer or an automatically retried request.
Mathematical accuracy and token caps alone do not trigger stopping. This keeps
operational supervision separate from the frozen method comparison.

The acceptance fixtures test health thresholds, planned stops, observer failures,
process scoping and an isolated native journal owner's termination. The live
experiment continues with unchanged generation/source pins. This monitoring
publishes local progress; it does not schedule future chat notifications.

** Terminal progress and provisional reasoning benefit

Run =just book-full500-status= in another terminal for an immediate report and
updates every ten minutes. Supply =60= for minute updates or =--once= for one
report. This read-only viewer consumes existing MLPL scoring snapshots and
watchdog history; it starts no worker and Ctrl-C stops only the viewer.

Progress is accounted calls divided by 2500: 500 direct calls, 500 greedy
chain-of-thought calls and 1500 voting samples. Errors and interruptions count
as terminal accounting and remain visible separately. ETA extrapolates from
roughly the last hour of completed calls, displaying hours remaining and a
local finish time. Stale observations, alerts or zero progress suppress ETA.
Response-length differences across questions can shift the projection.

The viewer also reports provisional direct/CoT/voting accuracy and paired
gains/losses on the same cases completed successfully by all three methods.
Scoring snapshots refresh at session boundaries, approximately every fifteen
minutes. The diagnostic cohort excludes unfinished or failed groups; it does
not replace the primary 500-case denominators or claim full-set accuracy.
The author-ordered prefix can be unrepresentative. These diagnostics measure
answer correctness under the existing verifier, not the validity of every
reasoning step, and do not trigger score-based early stopping.
