* The research question and our present result

Can we improve checked answers by giving a model an explicit reasoning
procedure, more inference compute, or training with verifiable rewards?
This report follows Sebastian Raschka's
[[https://www.manning.com/books/build-a-reasoning-model-from-scratch][Build a Reasoning Model (From Scratch), Manning]] and its
[[https://github.com/rasbt/reasoning-from-scratch][Python/PyTorch companion]], using independently written MLPL implementations
and a local GPU backend for the live experiment.

*We have a working reasoning experiment, but have not yet demonstrated that
our own model benefits from reasoning.* The distinction is between three
claims, each requiring different evidence:

| Claim | Present evidence | Verdict |
|-------+------------------+---------|
| Our independently implemented pipeline behaves correctly | Tiny forward/cache goldens, sampling, verification and refinement tests | Demonstrated on fixtures |
| A pretrained model produces correct multi-step solutions through our pipeline | Saved Qwen3 8B answers checked by MLPL | Demonstrated on five authored examples |
| Our reasoning method or training makes answers better | Frozen paired pilot: zero thinking gains, one truncation regression; no language-model training here yet | Not demonstrated |

“From scratch” describes implementing the methods, not pretraining a
language model from random weights. Our planned learning experiment starts
from a pretrained base and must show improvement over that same checkpoint.

The live model is externally pretrained Qwen3 8B Q6_K. Our own MLPL
Qwen3-0.6B-Base forward implementation has not completed real-model
generation. Therefore the honest milestone is *working inference and
measurement infrastructure*, not “our from-scratch model reasons, but
ineffectively.” We have not reached that latter claim yet.

The initial experiment found five correct answers without thinking and two
with thinking. All three thinking failures stopped at the output-token cap.
Doubling the cap to 3,072 restored thinking to five correct answers, with
no truncations. It still took 204.74 seconds versus 39.16 seconds for direct
answers. We fixed completion; we have not shown a quality benefit.

The new frozen six-problem pilot also finds no thinking gains across two
seeds, with one truncation regression and 5.85 times the request time. A
shared multiple-choice verifier false negative is reported separately below.

* How the book, Python, and MLPL fit together

The book supplies the progression: generate text, evaluate it, allocate
inference-time compute, refine solutions, then learn from rewards and
teacher examples. The Python companion makes those methods concrete with
PyTorch. We express the corresponding algorithms and contracts in MLPL,
with Org/Babel serving as executable explanation and reproducible analysis.
No book prose or Python source has been copied into our implementation.

| Book stage | Python companion role | Our working approach | Evidence still needed |
|------------+-----------------------+----------------------+-----------------------|
| Generation, chapter 2 | Model and decoding implementation | Tiny MLPL forward/cache parity; live native GPU inference | Real-weight MLPL forward feasibility |
| Evaluation, chapter 3 | Check mathematical answers | MLPL boxed extraction, normalization, exact arithmetic and attempt accounting | Broader evaluation with the corrected verifier |
| Scaling, chapter 4 | Spend more inference compute | Seeded sampling/voting fixtures; live thinking-budget comparison | Accuracy versus total cost |
| Refinement, chapter 5 | Revise candidate solutions | Bounded critique/revision and selection contracts | Gains without access to reference answers |
| RL, chapters 6–7 | Learn from verifiable rewards | Reward arithmetic and scalar autograd demonstration below | A trained policy with held-out reward gains |
| Distillation, chapter 8 | Learn from teacher outputs | Native teacher generation is available | Checked corpus and trainable student |

Sources: [[https://github.com/rasbt/reasoning-from-scratch#table-of-contents][companion chapter map]] and
[[https://www.manning.com/books/build-a-reasoning-model-from-scratch][publisher's description]]. This is a method comparison, not a measured
Python-versus-MLPL benchmark. We have not run the Python implementation
against these prompts, and make no cross-language accuracy or speed claim.

A future implementation comparison must match checkpoint, tokenizer,
precision, prompt/template, examples, sampling, stopping rules and hardware.
Compare deterministic logits or token ids first, then separate loading,
prefill, decoding and verification timings. Changing from a 0.6B base model
to an 8B instruction/thinking model is a model change, not a language-speed
comparison.

* The working experiment: generate, finish, verify, retain

** Division of responsibility

| Layer | Responsibility |
|-------+----------------|
| MLPL | Problems, prompt version, seed, output budget, extraction, verification, full attempt accounting |
| Existing Rust HTTP dynamic library | Bounded transport to the local model service |
| Ollama native GPU backend | Tokenization, resident weights, forward pass, sampling and KV cache |
| Shell runner | Identity checks and provenance capture |

The live path is *MLPL → Rust HTTP extension → Ollama → MLPL verifier*.
Large weights and caches stay resident in the backend. This lets us study
reasoning methods on the available 16 GiB GPU today. It is inference-only:
there is no gradient connection from the external model to MLPL parameters.

For each problem we render a versioned prompt that requests a boxed final
answer. The expected answer is never sent to the model. We save the request,
complete raw response, generated thinking text, final answer and grade.
Only final content is graded; a correct number buried in thinking cannot
rescue an incorrect final answer.

A successful attempt must stop normally, have nonempty final content, and
pass the verifier. Token-limit stops, transport errors and malformed answers
remain in the denominator. This completion rule is deliberately conservative
and is the same for both modes. The transport uses Ollama's
[[https://docs.ollama.com/api/chat][chat API]] and [[https://docs.ollama.com/capabilities/thinking][thinking control]].

** A worked solution and what it proves

Take three red and two blue balls, and draw two without replacement.
There are ten unordered pairs. Three pairs are all red and one is all blue,
so the probability of matching colors is =(3+1)/10 = 2/5=.

The saved non-thinking response follows that calculation and ends with
=\boxed{\frac{2}{5}}=. Our MLPL verifier normalizes the fraction and accepts
it against the independent reference =2/5=. It took 288 generated tokens
and 7.72 seconds in the original run. This demonstrates a correct generated
multi-step solution and a working checker. It does not establish that a
thinking switch improves the answer, or that the explanation is a faithful
transcript of internal computation.

** Exact controls

| Item | Value |
|------+-------|
| Model tag | =qwen3:8b-q6= |
| Model size / quantization | 8,190,735,360 parameters / Q6_K |
| Runtime | Ollama 0.24.0 |
| Thinking modes | Off, then on |
| Seed | 42 for every attempt |
| Temperature / top-p / top-k | 0.6 / 0.95 / 20 |
| Repeat penalty | 1 |
| Context / maximum new tokens | 4096 / 1536 initially; 3072 follow-up |
| Prompt version | =boxed-v1= |
| Dataset | Five authored =authored-demo-v1= cases |
| Extraction | Last valid box from final content only |
| HTTP deadline / response bound | 120 seconds / 1 MiB |

The request includes the problem but never its expected answer. The model
returns final content separately from its generated thinking text. We save
both, but only the final content is eligible for grading. The protocol is
based on Ollama's [[https://docs.ollama.com/api/chat][chat API]] and [[https://docs.ollama.com/capabilities/thinking][thinking controls]].

For completion accounting, =done_reason= must be =stop=, the runtime must
report completion, and the final content must be nonempty. A result stopped
by the token limit is incomplete even if a partial answer appears earlier.
This is a conservative, predeclared demo rule, not a universal requirement
for every possible evaluation.

** Why thinking appeared worse

The cap covers generated thinking and final-answer tokens together. The
three failed thinking attempts each reached exactly 1,536 tokens and
returned =done_reason=length=. Those are completion failures, not three
completed incorrect mathematical answers. The longer route ran out of
space before satisfying the same grading contract.

For these easy questions, the direct mode already achieved five out of
five. There is no headroom for a measured correctness gain on this sample.
Longer thinking could at best tie that score, while spending more tokens.
This set is useful for testing the pipeline and diagnosing truncation;
it cannot demonstrate a general advantage from reasoning.

The [[https://huggingface.co/Qwen/Qwen3-8B#best-practices][Qwen3 model card]] recommends ample output allowance and mode-specific
sampling. Its suggested thinking temperature/top-p/top-k are 0.6/0.95/20;
we use those values in both modes to hold sampling controls constant.
The non-thinking recommendation is 0.7/0.8/20, which is a separate future
comparison. Our short demo budget is not the model card's full benchmark
budget. We change one control at a time rather than attribute every
possible improvement to the thinking switch.

All three previously truncated answers now finish correctly: probability at
1,603 tokens, remainders at 2,005, and work rate at 1,815. Their thinking

fragment is a prefix of the completed response. Across all ten pairs, the
requests differ only in the output cap. This is direct evidence that the
old cap cut off these otherwise successful responses.

Thinking now ties direct answers at five out of five, but uses 7,602 versus
1,432 tokens and 204.74 versus 39.16 seconds (5.23 times the wall time).
The fix restores completion; it does not demonstrate a quality advantage.
For this sample, direct answers are the more efficient operating point.

The runner now exposes =DEMO_MAX_NEW= and defaults to 3072; use
=DEMO_MAX_NEW=1536= to reproduce the old cap. This is a development-set
diagnosis selected after inspecting failures, not a held-out quality claim.
A fixed seed does not guarantee identical output on all runtime/hardware
configurations. The 4,096-token context leaves room for these short prompts;
the unchanged transport deadline is 120 seconds per request. Harder problems
may need more context and a transport design allowing longer generation.
The current cap is a tested demo setting, not a universal reasoning budget.


** Replay the original grades in MLPL

The following block recomputes final-answer grades from raw saved responses,
checks them against the recorded grades, and verifies the original counts
and token totals. It does not contact the model or trust the stored score.

#+name: replay-grades
#+begin_src mlpl
# Replay every saved attempt, using the production verifier and explicit completion rule.
include "../lib/text/text.mlpl";
include "../lib/verify/number.mlpl";
include "../lib/verify/expr.mlpl";
include "../lib/verify/extract.mlpl";
include "../lib/verify/normalize.mlpl";
include "../lib/verify/grade.mlpl";
include "../lib/eval/data.mlpl";

dataset = u:eval_load_jsonl_text(read_text("docs/results/native-demo-2026-09-29.jsonl")?, "recorded-demo", {})?
mode = 0
matches = 1
while lt(mode, 2) {
  attempted = 0;
  correct = 0;
  truncated = 0;
  tokens = 0;
  seconds = 0;
  index = 0;
  while lt(index, dataset.count) {
    row = u:eval_record(dataset, index)?;
    if eq(row.think, mode) {
      raw = parse_json(row.response_json)?;
      complete = eq(raw.done, 1) * str_eq(raw.done_reason, "stop") * gt(str_len(u:text_trim(raw.message.content)), 0);
      grade = complete * u:verify_grade_response(raw.message.content, row.answer, "boxed_only");
      matches = matches * eq(grade, row.correct) * eq(complete, row.complete);
      attempted = attempted + 1;
      correct = correct + grade;
      truncated = truncated + str_eq(raw.done_reason, "length");
      tokens = tokens + raw.eval_count;
      seconds = seconds + raw.total_duration / 1000000000
    };
    index = index + 1
  };
  print("think:", mode, "attempted:", attempted, "correct:", correct, "truncated:", truncated, "tokens:", tokens, "native_seconds:", seconds);
  matches = matches * eq(attempted, 5) * eq(correct, if mode { 2 } else { 5 }) * eq(tokens, if mode { 6787 } else { 1432 });
  mode = mode + 1
}
if matches * eq(dataset.count, 10) {
  ok("all ten grades and aggregate checks reproduced")
} else {
  err("recorded results disagree with independent replay")
}
#+end_src

* A frozen held-out pilot: does the benefit transfer?

We next tested six MATH-500 problems that were not used in our five-case
prompt/budget development. Selection used the first six unique ids ranked
by SHA-256 of =native-heldout-v1:= followed by the id. We committed
[[https://github.com/sw-ml-study/reasoning-from-scratch/blob/main/docs/heldout-pilot-protocol.md][the protocol]] and
[[https://github.com/sw-ml-study/reasoning-from-scratch/blob/main/docs/results/heldout-pilot-v1-selection.jsonl][selection hashes]] in =826f467= before inference. We did not choose problems
based on whether they helped thinking mode.

Each problem ran with seeds 42 and 43 in both modes, giving 24 attempts.
We alternated mode order within pairs. Both modes received 12 calls with
the same 3,072-token cap and 120-second request deadline. This matches the
maximum allowance, not actual compute consumed. Temperature, top-p/top-k,
model, prompt and context were unchanged. No failed answer was replaced.

This is held out from *our development*, not necessarily from the external
model's pretraining. Public MATH-500 contamination is unknown. Six problems
are too few to establish a broad quality advantage, especially with repeated
seeds on the same questions.

** Verifier review is separate from the primary score

One selected multiple-choice problem exposed a false negative in our
normalizer. All four completed responses selected the correct option,
but a bare letter did not match the parenthesized letter inside a LaTeX
text wrapper. An independently authored diagnostic reproduces this class:
=\boxed{A}= matches =A=, but not =\text{(A)}= in the frozen v1 verifier.

These four primary failures are not mathematical failures by the model.
The public manual-review record identifies them individually. The primary
scores above retain the frozen verifier; the corrected analysis below carries
the new =choice-v2= verifier version. This finding is an application-level MLPL change,
not a missing language feature or an interpreter optimization task.

Final answers also do not certify every explanation step. One direct answer
selected the correct option but incorrectly described constant cylindrical
radius as a sphere in a distractor discussion. That is an explanation error
separate from final-answer correctness. A future reasoning-quality audit
should sample intermediate steps as well as final answers.

** Corrected automatic grading: choice-v2 post-hoc replay

We regraded all 24 retained responses without generating new answers.
Exactly four grades changed, matching the independently recorded manual
review. Historical v1 grading still reproduces every original score.

| Seed | Direct correct | Thinking correct | Thinking gains | Thinking regressions |
|------+----------------+------------------+----------------+----------------------|
| 42 | 6/6 | 5/6 | 0 | 1 |
| 43 | 6/6 | 6/6 | 0 | 0 |

The correction accepts a whole parenthesized uppercase ASCII letter, with
an optional whole LaTeX text wrapper. Synthetic native tests reject changed
letters, lowercase parenthesized variables, tuples, signs, algebra, words,
nested parentheses and incomplete wrappers. This bounded convention cannot
distinguish an uppercase choice from an identically written isolated symbol;
it is not general symbolic simplification.

This is *post-hoc verifier repair*, not new held-out evidence or model
improvement. No costs, completions or token counts changed. The remaining
thinking failure exhausted its 3,072-token allowance. The six independent
questions are too few to establish general accuracy: even 6/6 has a 95%
Wilson interval of approximately 61–100%. Repeated seeds are not independent
new questions. Public numeric results and provenance are stored in the
=native-heldout-choice-v2= files under =docs/results/=.

* From “it produces reasoning” to “reasoning helps”

** An operational success criterion

The next milestone is higher held-out correctness from a declared reasoning
method, with its extra cost measured. Compare the same questions in both
modes and count both directions: direct wrong / reasoning right, and direct
right / reasoning wrong. Report the net paired gain, uncertainty, completion
rate, median and tail latency, and total tokens. Preserve failures and all
seeds. A longer explanation alone is not progress on this criterion.

Use a development set to select budgets and prompts, then freeze them before
opening a new held-out set. Include a range of difficulty chosen independently
of these model outputs. A pilot estimates runtime and detects gross problems;
a larger paired experiment is needed for a persuasive gain. Do not filter
held-out questions after seeing which ones make reasoning look good.

Compare two useful operating points separately: equal maximum budgets,
and equal total compute across methods. For example, one longer thinking
response can be compared with several short independent responses plus
answer voting. Do not use the held-out reference answer to choose a candidate;
it is for final evaluation only. Voting agreement is not itself correctness.

** Is the model too small?

Capacity is a plausible constraint, but our measurements do not identify
one. The 0.6B path has no real generation result, and the demonstrated 8B
path was budget-limited on an easy set. Neither isolates parameter count.

There is also no universal rule that small models cannot benefit from
reasoning training. The [[https://huggingface.co/deepseek-ai/DeepSeek-R1-Distill-Qwen-1.5B][DeepSeek distilled-model report]] publishes reasoning benchmark results for
1.5B and larger students trained on teacher-generated examples. That is
evidence that useful reasoning behavior can be taught at small sizes;
it does not prove spontaneous emergence, nor that our untrained 0.6B
checkpoint will show the same benefit.

Test a size hypothesis with a controlled ladder: related model families,
matched training status where possible, identical tasks, budgets and seeds.
Distinguish base from instruction-tuned or reasoning-distilled models.
If smaller models fail to produce useful candidates even at adequate
budgets, training quality, distillation and a larger model become sensible
next experiments. Merely increasing token limits cannot create missing
skills, and selecting a larger checkpoint cannot prove our training works.

** ICL, feedback in context, and actual training are different tests

In-context learning (ICL) would require comparing zero-shot prompts with
relevant demonstrations, on fresh problems. Our current prompt contains
one problem and no demonstrations; this run does not measure ICL.

If “ICRL” means in-context reinforcement learning, test whether a sequence
of attempts and reward feedback improves later choices without weight
updates. Use a reset-context control, equal total attempts, and a task
where feedback is available without revealing the held-out solution.
The current independent requests contain no such feedback history, so
we have not tested that mechanism either.

GRPO is a different experiment: update policy parameters using relative
rewards, then evaluate the resulting checkpoint on unseen cases. A useful
small-model sequence is supervised learning or checked teacher distillation
first when the policy rarely finds any correct answer, followed by reward
optimization where groups contain informative successes and failures.
This is our proposed experiment order, not a claim of a measured result.

** Concrete improvement order

*** Can we lift the token limit, and what is missing?

Yes. The native demo currently caps output at 3,072 tokens, uses a
4,096-token context and requests a 120-second HTTP timeout. These are
application settings, not the GPU's capacity. The next development experiment
will test a larger bounded allowance, initially 8,192 output tokens with
additional context space for the prompt, after checking model limits, timeout
support and measured GPU residency. It must retain the original truncated
attempt and report whether the longer run actually finishes correctly.
Unlimited generation would make neither a reliable demo nor a fair comparison.

The working Qwen3 8B path already executes forward passes and generation
through Ollama on the GPU. Our own MLPL implementation also contains the
Qwen3 forward algorithm and cached decoding, validated on tiny fixtures.
What it lacks is demonstrated practical real-checkpoint generation within
the 32 GiB *CPU virtual-address-space* test budget. The smoke script imposes
that ceiling with =ulimit -v 33554432=; it is a containment choice, not a
hardware limit or a model requirement. The host has about 251 GiB RAM
(about 241 GiB available at this check), so a larger bounded diagnostic is
feasible. Failure at 32 GiB does not prove failure at every larger budget.
The selected MLPL interpreter uses CPU f64 arrays: the roughly 1.19 GB BF16
weight payload expands to roughly 4.77 GB before temporary copies. The
recorded run reached about 31 GiB resident memory without emitting a token.
That CPU allocation is separate from the 16 GiB of GPU VRAM; the GPU was
not used by the reference attempt. Raising output tokens in the native demo cannot repair
the MLPL path's memory costs, and raising a memory cap does not make execution
more efficient. The short-term route remains native inference offload;
any additional resident-model extension belongs in the sibling extension
project through a documented work request. Differentiable execution and
project-trained reasoning remain separate, unproved milestones.

*** Experiments after the verifier correction

1. Remove avoidable truncation with a measured output budget and retain the
   wall-clock bound. Measure whether final answers actually complete.
2. The frozen pilot is complete: zero gains, one truncation regression,
   and four choice-format false negatives now corrected in choice-v2.
   Retain the primary results, and confirm any method changes on a
   new frozen holdout.
3. Test voting, checked refinement and few-shot demonstrations as separate
   interventions. Keep selection independent of the reference answer.
4. Compare related model sizes only after controlling budgets and training
   status. This tests the capacity hypothesis rather than assuming it.
5. Train a tiny policy with verifiable rewards and demonstrate held-out
   improvement against its initial checkpoint and a no-update control.
6. Move to a small language-model student with checked teacher examples,
   then assess whether GRPO adds value. Native inference can supply teacher
   outputs; a differentiable training backend is still required.

These are two parallel research tracks: useful inference methods with the
working pretrained backend, and evidence that our own learning algorithms
improve a policy. Success on one must not be reported as success on both.

* Training: one real toy update, and the work still required for an LLM

Turning on a pretrained model's thinking mode does not train it. No weights
changed during either inference comparison. The MLPL verifier can supply a
reward signal, but reward computation and parameter optimization are
separate operations.

** From checked answers to relative rewards

Suppose four independently sampled answers receive rewards =[1,1,0,0]=.
Subtracting the group mean identifies better and worse samples relative to
that group. Scaling by the unbiased sample standard deviation plus epsilon
gives a dimensionless advantage. A constant-reward group supplies no
relative preference. This block illustrates that arithmetic only; it does
not implement the complete GRPO objective or a policy update.

#+name: reward-advantages
#+begin_src mlpl
# Educational reward normalization, not a trained policy.
rewards = [1, 1, 0, 0]
centered = rewards - mean(rewards)
deviation = sqrt(reduce_add(centered * centered) / (tally(rewards) - 1))
advantages = centered / (deviation + 0.000001)
constant = [1, 1, 1, 1]
constant_advantages = (constant - mean(constant)) / 0.000001
print("rewards:", rewards)
print("sample deviation:", deviation)
print("advantages:", advantages)
print("constant-group advantages:", constant_advantages)
if eq(reduce_add(advantages), 0) * equal(constant_advantages, [0, 0, 0, 0]) {
  ok(1)
} else {
  err("reward-normalization check failed")
}
#+end_src

Reward alone does not specify which token probabilities should change.
An LLM training implementation also needs differentiable sequence log
probabilities, an explicit masking convention, policy ratios, clipping and
any reference-policy regularization, an optimizer, and checkpointing.
Those steps must be tested before a reward improvement can be called an
LLM training result.

** A small, actual MLPL training experiment

To make the difference concrete, fit the scalar model =prediction=w*x= to
=y=2*x= for =x=[1,2,3,4]=. This is deterministic supervised regression,
not reasoning-model training. Initialize =w=0=, compute the gradient of the
mean squared error, and make six gradient-descent updates at rate 0.05.

The loss is =7.5*(w-2)^2=, so its derivative is =15*(w-2)=. Each update
therefore quarters the distance from =w= to 2. This independent analytic
recurrence gives exact acceptance values: after six steps
=w=1.99951171875= and loss =0.0000017881393432617188=.
The native test suite checks these values, rather than merely asserting
that some number decreased.

#+name: toy-sgd
#+begin_src mlpl
# Actual six-step scalar regression; no language-model weight is changed.
w = param[1]
w = [0]
x = [1, 2, 3, 4]
y = 2 * x
print("step 0 weight:", w, "loss:", mean((w * x - y) * (w * x - y)))
step = 0
while lt(step, 6) {
  derivative = grad(mean((w * x - y) * (w * x - y)), w);
  w = w - 0.05 * derivative;
  step = step + 1;
  print("step:", step, "weight:", w, "loss:", mean((w * x - y) * (w * x - y)))
}
final_loss = mean((w * x - y) * (w * x - y))
if equal(w, [1.99951171875]) * eq(final_loss, 0.0000017881393432617188) {
  ok("scalar training matches the analytic recurrence")
} else {
  err("scalar training differs from its golden result")
}
#+end_src

** The next training evidence we would require

Start with a tiny trainable policy on a synthetic task with known rewards.
Keep training and evaluation examples separate; measure a before/after
change over fixed evaluation seeds; retain the old policy and a no-update
control. Test constant rewards, masking, clipping boundaries and gradient
signs. Only then test real-model gradient and memory feasibility.

The external native model can later generate candidate teacher responses,
but responses must be checked before becoming a training corpus. Record
which model produced them, preserve licensing/provenance, and prevent
held-out evaluation questions from entering training. A native inference
session is not a substitute for a differentiable student training path.
