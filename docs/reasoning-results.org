* The result in one page

We now have a working local GPU demonstration that accepts a mathematics
problem, generates an answer, and checks its final result in MLPL. The live
path is *MLPL → Rust HTTP dynamic library → Ollama native inference → MLPL
verifier*. It uses an already pretrained Qwen3 8B Q6_K model. We did not
train that model, and this path does not execute our MLPL Qwen3 forward pass.

The distinction matters. The project's own Qwen3-0.6B-Base implementation
loads its checkpoint, but still exhausts a 32 GiB CPU address-space limit
before generating a token. The native workaround makes a useful demo
possible without waiting for interpreter optimization. Both outcomes belong
in the record.

The first complete MLPL/extension rehearsal answered the shopping problem
correctly in 13.6 seconds. A subsequent ten-attempt comparison found:

| Configuration | Correct / attempted | Truncated | Generated tokens | MLPL wall time |
|---------------+---------------------+-----------+------------------+----------------|
| Thinking off  | 5 / 5               | 0         | 1,432            | 42.17 s        |
| Thinking on   | 2 / 5               | 3         | 6,787            | 184.47 s       |

Both modes used the same five authored problems, seed 42, and a 1,536-token
output cap. Thinking mode spent more of that budget before producing a
final answer. Three outputs hit the cap and failed the declared completion
rule. This is a *budget-limited demonstration result*, not an estimate of
broad reasoning ability and not evidence that thinking is always worse.

* Read, replay, rerun: three different activities

This document is both a report and an Emacs Org/Babel notebook using
=ob-mlpl=. Reading or exporting it does not load a model or make network
requests. Its recorded results are preserved in the Org source and HTML.

There are three levels of reproducibility:

1. *Replay the analysis:* read the committed ten attempts, recompute grades
   and aggregates in MLPL, and reproduce the toy calculations. This is
   offline and does not need a GPU.
2. *Repeat inference:* run the recorded prompts and settings against the
   pinned local model/runtime. This requires the model and GPU backend.
   Sampling and runtime details can change the exact generated text.
3. *Reproduce a comparative research claim:* match models, data, prompts,
   budgets and metrics across implementations, then repeat with enough
   examples and seeds. We have not yet done this for MLPL versus Python.

* Experiment 1: explain the memory failure before changing the budget

** CPU memory and GPU memory are different resources

The 32 GiB limit was Linux =RLIMIT_AS=, a bound on the CPU process's virtual
address space. It was a containment budget on a machine with approximately
251 GiB RAM. It was not chosen from the GPU's capacity and was not evidence
that the model inherently requires 32 GiB. The measured interpreter builds
were CPU-only; they did not put the model on the 16 GiB RTX 5060 Ti.

The real base checkpoint contains 596,049,920 parameters. Stored as BF16,
its tensor payload is 1,192,099,840 bytes. The interpreter represents the
unpacked numerical arrays with f64 elements, so the same values occupy four
times as many bytes before any copies. The following calculation is exact
integer arithmetic expressed in MLPL; the final units are binary GiB.

#+name: memory-arithmetic
#+begin_src mlpl
# Exact storage accounting; this is not an allocation or model run.
parameters = 596049920
bf16_bytes = parameters * 2
f64_bytes = parameters * 8
print("BF16 payload bytes:", bf16_bytes)
print("f64 payload bytes:", f64_bytes)
print("f64 payload GiB:", f64_bytes / 1073741824)
print("storage expansion:", f64_bytes / bf16_bytes)
if eq(bf16_bytes, 1192099840) * eq(f64_bytes, 4768399360) {
  ok(1)
} else {
  err("storage accounting disagrees with checkpoint manifest")
}
#+end_src

The working set also includes evaluated arguments, saved bindings,
projection temporaries and caches. A language runtime can copy the same
large record several times along a short call chain. This is why model
file size is not a useful upper bound on process memory here.

** What changed, and what did not

| Attempt | Loading outcome | Generation outcome | Interpretation |
|---------+-----------------+--------------------+----------------|
| Original CPU loader | Did not finish in 600 s | Never started | Loading was the first measured bottleneck |
| Scoped loader on =cd3cd03f= | 101.45 s | Allocation failure under 32 GiB | Loader improvement did not make inference viable |
| Shipped frame fix on =49c15b3e= | 102.89 s | Same-size allocation failure; status 134 | Unrelated-global fix alone was insufficient |

The newest upstream code journals the names a function writes instead of
snapshotting every unrelated global binding. Our scalar-call probe changes
from failure to success: small/large cases took 1.11/1.25 ms, below a 10 ms
acceptance threshold. All original 148 native tests also passed. We built
already-shipped upstream code in an isolated directory; we did not modify
or optimize the interpreter in this task.

Nevertheless, the unchanged real smoke failed a 1,244,659,712-byte
allocation after loading. The process lasted 114 seconds, exited 134, and
had sampled peak VmHWM 33,011,188 KiB. The child had core-file limit zero.
No tokens were produced. The 114 seconds is process lifetime, *not generation
throughput*. An earlier status 137 came from manually stopping a core dump;
it must not be described as a kernel OOM kill.

These measurements justify the user's short-term extension workaround.
They do not justify simply declaring the GPU too small or increasing CPU
memory and calling the problem solved.

* Experiment 2: put the resident model behind a native boundary

** Division of responsibility

| Layer | Responsibility | Evidence |
|-------+----------------+----------|
| MLPL | Authored problems, prompt text, seed and budgets, final-answer verification, attempt accounting | Native tests and replay block below |
| Rust HTTP dynamic library | Bounded request/response transport | Existing pinned =demo-extensions= public facade and =.so= |
| Ollama native backend | Tokenization, model weights, forward pass, sampling and cache | Runtime response and GPU residency metadata |
| Shell runner | Preflight identity checks and provenance files | Thin opt-in recipe; no reasoning or scoring logic |

The extension itself does not execute tensor kernels. It connects MLPL to
a native inference service that already does. No weights or KV cache cross
the MLPL boundary, so deep copies of those arrays cannot arise in this
adapter. The model remains resident in the backend between requests.

This route is inference-only. An HTTP request has no differentiable link
back to MLPL parameters. It is suitable for a live pretrained demo and
potential teacher-output collection. It does not make GRPO training of
our MLPL model work automatically.

** Exact controls

| Item | Value |
|------+-------|
| Model tag | =qwen3:8b-q6= |
| Model size / quantization | 8,190,735,360 parameters / Q6_K |
| Runtime | Ollama 0.24.0 |
| Thinking modes | Off, then on |
| Seed | 42 for every attempt |
| Temperature / top-p / top-k | 0.6 / 0.95 / 20 |
| Repeat penalty | 1 |
| Context / maximum new tokens | 4096 / 1536 |
| Prompt version | =boxed-v1= |
| Dataset | Five authored =authored-demo-v1= cases |
| Extraction | Last valid box from final content only |
| HTTP deadline / response bound | 120 seconds / 1 MiB |

The request includes the problem but never its expected answer. The model
returns final content separately from its generated thinking text. We save
both, but only the final content is eligible for grading. The protocol is
based on Ollama's [[https://docs.ollama.com/api/chat][chat API]] and [[https://docs.ollama.com/capabilities/thinking][thinking controls]].

For completion accounting, =done_reason= must be =stop=, the runtime must
report completion, and the final content must be nonempty. A result stopped
by the token limit is incomplete even if a partial answer appears earlier.
This is a conservative, predeclared demo rule, not a universal requirement
for every possible evaluation.

** Recompute grades from saved answers with MLPL

This block reads the ten committed attempts and runs the production verifier
again. It ignores the stored correctness field when computing the grade,
then checks that its recomputation agrees. It also verifies the sample
count and aggregate token totals. There is no inference call in this block.

#+name: replay-grades
#+begin_src mlpl
# Replay every saved attempt, using the production verifier and explicit completion rule.
include "../lib/text/text.mlpl";
include "../lib/verify/number.mlpl";
include "../lib/verify/expr.mlpl";
include "../lib/verify/extract.mlpl";
include "../lib/verify/normalize.mlpl";
include "../lib/verify/grade.mlpl";
include "../lib/eval/data.mlpl";

dataset = u:eval_load_jsonl_text(read_text("docs/results/native-demo-2026-09-29.jsonl")?, "recorded-demo", {})?
mode = 0
matches = 1
while lt(mode, 2) {
  attempted = 0;
  correct = 0;
  truncated = 0;
  tokens = 0;
  seconds = 0;
  index = 0;
  while lt(index, dataset.count) {
    row = u:eval_record(dataset, index)?;
    if eq(row.think, mode) {
      raw = parse_json(row.response_json)?;
      complete = eq(raw.done, 1) * str_eq(raw.done_reason, "stop") * gt(str_len(u:text_trim(raw.message.content)), 0);
      grade = complete * u:verify_grade_response(raw.message.content, row.answer, "boxed_only");
      matches = matches * eq(grade, row.correct) * eq(complete, row.complete);
      attempted = attempted + 1;
      correct = correct + grade;
      truncated = truncated + str_eq(raw.done_reason, "length");
      tokens = tokens + raw.eval_count;
      seconds = seconds + raw.total_duration / 1000000000
    };
    index = index + 1
  };
  print("think:", mode, "attempted:", attempted, "correct:", correct, "truncated:", truncated, "tokens:", tokens, "native_seconds:", seconds);
  matches = matches * eq(attempted, 5) * eq(correct, if mode { 2 } else { 5 }) * eq(tokens, if mode { 6787 } else { 1432 });
  mode = mode + 1
}
if matches * eq(dataset.count, 10) {
  ok("all ten grades and aggregate checks reproduced")
} else {
  err("recorded results disagree with independent replay")
}
#+end_src

** What the difference means

*** A generated solution, checked step by step

In the saved probability/off response, the model counted ten unordered
pairs, then three all-red pairs and one all-blue pair, and reduced 4/10 to
2/5. Those steps match an independent combinatorial calculation. Its final
answer was =\boxed{\frac{2}{5}}= and the MLPL normalizer/verifier accepted
that as equivalent to the reference =2/5=. The request generated 288 tokens
and completed in 7.72 seconds.

The corresponding thinking/on attempt reached 1,536 tokens without a
complete final answer. Its longer generated text does not override the
completion rule. This pair makes a useful live explanation: an answer must
both arrive within the resource budget and satisfy the verifier.

In the shopping/on response, the model computed 3×4=12, 5×2=10, total 22,
then 30−22=8. Its saved thinking text repeated the calculation and checked
the problem wording. That repetition is observable generated behavior;
whether it improves reliability requires further experiments. The full
texts, not just these descriptions, are preserved in the research JSONL.

*** Budget interpretation

Thinking mode generated approximately 4.74 times as many tokens and took
4.37 times as much MLPL wall time. Under this cap, it completed only two
answers. The direct mode's short solutions fit within the cap and all five
verified. The three missing final answers are operational failures, even
if the model's preceding text contained useful intermediate calculations.

This does not isolate the causal value of reasoning. The mode changes the
model's response behavior; there is only one seed per case; off-mode calls
ran first; and the questions are small and selected for a demonstration.
A larger cap might rescue truncated responses, but that would be a new
experiment with a different cost allowance. We did not silently grant extra
tokens until answers looked good.

For the afternoon presentation, use the shopping question with thinking
on, then probability with thinking off. Show the comparison table as a
lesson in budgeting and measurement. Do not conceal the three truncated
attempts or present 5/5 as general mathematical competence.

** Why a numeric Python-versus-MLPL ranking would be misleading today

Our blocked native reference uses a 0.6B base checkpoint stored as BF16,
unpacked to CPU f64 arrays. The working demo uses a pretrained 8B model
quantized to Q6_K, with a different instruction/thinking behavior and native
GPU execution. Model size, training history, precision and hardware path
all differ. Comparing their timings or correctness would not measure a
language implementation effect.

A defensible future comparison should pin one checkpoint and tokenizer,
precision/quantization, exact prompt text, dataset ids, stop behavior,
sampling configuration and seed schedule. Separate cold loading, prefill,
decode and verification timings. For implementation parity, compare logits
or greedy token ids on a short deterministic fixture before comparing
aggregate accuracy. Use the same hardware and distinguish wall-clock
cost from output tokens per second. Report failures on both sides.

The present report therefore leaves Python throughput, Python accuracy on
these cases, and any MLPL/Python speed ratio *unmeasured*. Previously noted
book benchmark figures are not mixed into our demonstration score.

* Training: one real toy update, and the work still required for an LLM

Turning on a pretrained model's thinking mode does not train it. No weights
changed during the ten inference attempts. The MLPL verifier can supply a
reward signal, but reward computation and parameter optimization are
separate operations.

** From checked answers to relative rewards

Suppose four independently sampled answers receive rewards =[1,1,0,0]=.
Subtracting the group mean identifies better and worse samples relative to
that group. Scaling by the unbiased sample standard deviation plus epsilon
gives a dimensionless advantage. A constant-reward group supplies no
relative preference. This block illustrates that arithmetic only; it does
not implement the complete GRPO objective or a policy update.

#+name: reward-advantages
#+begin_src mlpl
# Educational reward normalization, not a trained policy.
rewards = [1, 1, 0, 0]
centered = rewards - mean(rewards)
deviation = sqrt(reduce_add(centered * centered) / (tally(rewards) - 1))
advantages = centered / (deviation + 0.000001)
constant = [1, 1, 1, 1]
constant_advantages = (constant - mean(constant)) / 0.000001
print("rewards:", rewards)
print("sample deviation:", deviation)
print("advantages:", advantages)
print("constant-group advantages:", constant_advantages)
if eq(reduce_add(advantages), 0) * equal(constant_advantages, [0, 0, 0, 0]) {
  ok(1)
} else {
  err("reward-normalization check failed")
}
#+end_src

Reward alone does not specify which token probabilities should change.
An LLM training implementation also needs differentiable sequence log
probabilities, an explicit masking convention, policy ratios, clipping and
any reference-policy regularization, an optimizer, and checkpointing.
Those steps must be tested before a reward improvement can be called an
LLM training result.

** A small, actual MLPL training experiment

To make the difference concrete, fit the scalar model =prediction=w*x= to
=y=2*x= for =x=[1,2,3,4]=. This is deterministic supervised regression,
not reasoning-model training. Initialize =w=0=, compute the gradient of the
mean squared error, and make six gradient-descent updates at rate 0.05.

The loss is =7.5*(w-2)^2=, so its derivative is =15*(w-2)=. Each update
therefore quarters the distance from =w= to 2. This independent analytic
recurrence gives exact acceptance values: after six steps
=w=1.99951171875= and loss =0.0000017881393432617188=.
The native test suite checks these values, rather than merely asserting
that some number decreased.

#+name: toy-sgd
#+begin_src mlpl
# Actual six-step scalar regression; no language-model weight is changed.
w = param[1]
w = [0]
x = [1, 2, 3, 4]
y = 2 * x
print("step 0 weight:", w, "loss:", mean((w * x - y) * (w * x - y)))
step = 0
while lt(step, 6) {
  derivative = grad(mean((w * x - y) * (w * x - y)), w);
  w = w - 0.05 * derivative;
  step = step + 1;
  print("step:", step, "weight:", w, "loss:", mean((w * x - y) * (w * x - y)))
}
final_loss = mean((w * x - y) * (w * x - y))
if equal(w, [1.99951171875]) * eq(final_loss, 0.0000017881393432617188) {
  ok("scalar training matches the analytic recurrence")
} else {
  err("scalar training differs from its golden result")
}
#+end_src

** The next training evidence we would require

Start with a tiny trainable policy on a synthetic task with known rewards.
Keep training and evaluation examples separate; measure a before/after
change over fixed evaluation seeds; retain the old policy and a no-update
control. Test constant rewards, masking, clipping boundaries and gradient
signs. Only then test real-model gradient and memory feasibility.

The external native model can later generate candidate teacher responses,
but responses must be checked before becoming a training corpus. Record
which model produced them, preserve licensing/provenance, and prevent
held-out evaluation questions from entering training. A native inference
session is not a substitute for a differentiable student training path.

* Measuring reasoning quality beyond the demo

** Define the observable target

A useful first target is final-answer correctness under a declared resource
budget. Keep attempted, completed, parseable and correct counts separate.
Include timeouts, malformed answers and truncations in the attempted
denominator. Report accuracy together with latency and generated tokens.
Do not substitute confidence, vote agreement or explanation length for a
checked result.

Correct final answers alone cannot prove that a written explanation
faithfully describes the model's internal computation. Review intermediate
mathematics on a separate sample, perturb problem numbers and wording, and
include cases that challenge superficial pattern matching. These checks
measure different properties and should remain separate in the report.

** Freeze the evaluation before looking at answers

The next queued experiment is a small frozen held-out pilot, followed by a
larger run only when its measured cost is acceptable. Choose the examples,
references, prompt version, seeds and stopping rules first. Compare modes
on exactly the same cases, retain every attempt, and report uncertainty.
If prompts or token limits are adjusted after inspecting failures, use a
new validation set for the final claim.

Match both the per-response limit and the total sampling budget when
comparing single responses with self-consistency or best-of-N. A method
that spends ten times as many tokens may be useful, but its cost must not
be hidden. A five-case demonstration is too small and too selected to
support a population accuracy claim; a narrow confidence interval would
not repair selection bias.

Weights and downloaded datasets remain outside version control. The
research records here contain our authored questions and model-generated
responses, not book text or copied Python code. Publishing the HTML does
not redistribute model weights.

The full fixture gate has 155 native tests and 27 declared capability
outcomes. A capability probe with an expected failure records a known
limitation; it is not a delivered feature. The reference implementation's
exact tangles are checked separately. These checks support software
correctness and report replay, not a broad model-quality claim.

Future interpreter work remains documented: shared immutable/COW arrays,
cheap container/partial access, bounded argument/frame copying with correct
scope and gradients, batched operations, and validated device dispatch.
If a direct in-process Rust inference library becomes necessary, keep model
and cache buffers behind typed generational handles, expose bounded
load/generate/close operations, and test lifecycle and memory limits. Today
we reuse the existing transport extension and proven native engine.

The next useful evidence is held-out quality and cost measurement. The
working demo already provides the foundation for that experiment.
